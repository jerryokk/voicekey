# 重构方案：UI 设计与后端结构

> 目标：让「手机当麦克风」这件事在界面上 5 秒内看懂，代码上每个文件只做一件事。

## 一、现状评估（实测，不是感觉）

### UI 的问题

| 问题 | 证据 | 影响 |
|---|---|---|
| 品牌色打架 | `style.css` 里 `--g1 #22c3ff / --g2 #7b5cff / --g3 #ff3d8b`、`--accent #6a5cff`（蓝紫粉，旧品牌）；而图标/托盘/二维码窗口已经是暖橙 `#d9552b` | 打开就是两种风格，最显眼的不专业 |
| 样式分散 | 全局 `style.css` 仅 65 行；`Recog.svelte` 自带 27 行、`Connect` 自带样式、`Qr` 自带样式 | 同类控件在不同页面长得不一样，改一处要改多处 |
| 圆角/密度混乱 | `--r:12px`，但 `.win` 下被覆盖成 `8px/4px`（macOS 遗留规则，Windows 上反而更硬） | Windows 上的观感比设计稿「紧一档」 |
| 首页没有「状态」 | 4 个平级页（手机接入/识别/输出/通用），第一页是配网 | 用户打开只看到二维码，不知道「现在能不能用」 |
| HUD 与主界面两套语言 | `Hud.svelte` 独立 51 行样式 | 浮层像个外挂，不像同一个产品 |

### 后端的问题

| 问题 | 证据 | 影响 |
|---|---|---|
| `controller.rs` 649 行 | 状态机 + 分段拼接 + 代际/超时 + 引擎编排 + 预开麦 + 上屏 + 托盘联动 | 改一处要读整文件，最难测的部分混在最难读的文件里 |
| `ui.rs` 287 行 | 托盘菜单 + 浮层定位 + 两个窗口 + 坐标换算 | 三个不相干的关注点挤在一起 |
| 无日志 | 改成 GUI 子系统后 stderr 不可见 | 出问题只能靠界面提示，用户无从反馈 |
| 错误被吞 | 大量 `let _ = ...` | 失败静默，和「没发生」无法区分 |
| 设置无版本 | `Settings` 直接序列化 | 字段演进只能靠 `serde(default)` 猜 |
| `remote/lib.rs` 376 行 | axum 路由 + WS 协议 + 会话归属 + 音频通道 | 协议与传输耦在一起 |

## 二、UI 设计

### 2.1 设计语言（统一到新 logo）

| 项 | 值 | 说明 |
|---|---|---|
| 主色 | `#d9552b`（暖橙）| 取自 logo 灯头，只用于「当前/激活/录音」 |
| 强调渐变 | `#ffa06a → #d9552b` | 仅头像、录音波形、进度条这类小面积 |
| 中性色 | `#16161a / #5c5f66 / #9a9ca3` | 文字三级 |
| 表面 | 浅色 `#f7f7f5` / 卡片 `#fff` / 深色 `#1b1b19` / `#232320` | 与二维码窗口同源 |
| 圆角 | 卡片 14 / 控件 9 / 胶囊 999 | 去掉 macOS 的 8/4 覆盖 |
| 间距 | 4 的倍数：4 / 8 / 12 / 16 / 24 / 32 | 单一节奏 |
| 字号 | 20 标题 / 13 正文 / 12 辅助 / 11 标签 | 4 档，不再出现 12.5 / 11.5 |
| 动效 | 120ms 控件、200ms 面板 | 只用于状态变化 |

### 2.2 信息架构（4 页 → 3 页，状态优先）

```
┌─────────────┬──────────────────────────────────────────┐
│  ⬤ VoiceKey │  连接                                     │
│             │  ┌────────────────────────────────────┐  │
│ ▸ 连接      │  │ ● 手机已连接  豆包输入法            │  │
│   渠道      │  │   在手机上按住说话，结果会打到这里  │  │
│   设置      │  │                        [显示二维码] │  │
│             │  └────────────────────────────────────┘  │
│             │                                          │
│             │  最近一句                                │
│             │  ┌────────────────────────────────────┐  │
│             │  │ 今天天气不错，我们下午一起去公园…   │  │
│             │  └────────────────────────────────────┘  │
│             │                                          │
│  ● 就绪     │  怎么用（3 步，首次打开时展开）           │
└─────────────┴──────────────────────────────────────────┘
```

- **连接**（默认页）：一张状态卡回答「能不能用」——手机连没连、隧道通不通、当前渠道、最近一句；二维码收进按钮，需要时右下角弹出（已有交互）。
- **渠道**：单选 + 多渠道组合，保留现有卡片思路但统一视觉与间距。
- **设置**：输出（上屏方式、流式开关）+ 通用（自启、主题）+ 关于，合并成一页分组，去掉一页只有一个开关的空旷感。

### 2.3 组件化（一次性收口）

```
app/src/lib/ui/
  tokens.css      颜色/间距/圆角/字号变量（唯一来源）
  base.css        按钮/开关/分段/输入 的基类
  Card.svelte     卡片容器（标题 + 内容）
  Row.svelte      设置行（主文案 + 说明 + 右侧控件）
  Switch.svelte   开关
  Segmented.svelte 分段选择
  StatusDot.svelte 状态点（就绪/连接中/异常）
  Button.svelte   主/次/危险 三档
```

页面只写「内容与组合」，不写视觉细节；`style.css` 缩到只留变量与 reset。

### 2.4 HUD 重做

- 胶囊：圆角 999、半透明毛玻璃、跟随主题
- 左侧状态点（录音=橙色呼吸 / 等待=琥珀 / 出错=红）
- 中间实时文字（单行截断），右侧渠道短名
- 宽度自适应 320–680，位置沿用现有 `caret` 逻辑

## 三、后端结构

### 3.1 模块拆分（行为不变，纯结构搬迁）

```
app/src-tauri/src/
  main.rs        启动装配、命令注册（<120 行）
  state.rs       AppState / RemoteStatus（集中）
  ipc.rs         #[tauri::command] 全部集中，只做参数校验与转发
  log.rs         文件日志（%LOCALAPPDATA%\VoiceKey\logs，按天，留 7 天）
  session/
    mod.rs       会话编排（原来 controller 的主循环）
    machine.rs   纯状态机：Idle / Single / Pick + 代际 + 超时（可单测，不碰 Tauri）
    segments.rs  分段拼接（从 controller 抽出）
    engines.rs   引擎注册、预热门、多路扇出
    output.rs    Typer / paste 决策（流式 or 一次性）
  windows/
    main_window.rs 设置窗口
    qr_window.rs   扫码弹窗（含右下角定位）
    overlay.rs     HUD（定位 + 显示）
  tray.rs        托盘菜单与事件（命令枚举化）
```

要点：

- **`machine.rs` 不依赖 Tauri**：输入 `Event`，输出 `Action`（Begin/Abort/Paste/Rows…），用纯 Rust 单测覆盖「接着说」「超时」「多渠道选行」。
- **命令枚举化**：托盘 id 从散字符串改成 `enum Cmd { ShowQr, Open, Quit, SetChannel(Channel) }`，解析一处、分支一处。
- **`ipc.rs`**：前端能调的只有 5 个命令，集中审阅。
- **日志**：`log.rs` 提供 `info!/warn!/error!` 宏，写文件；错误不再 `let _ =`。

### 3.2 `remote` crate 拆分

```
crates/remote/src/
  lib.rs        Service 门面（start / url / next_event / take_audio / handle）
  http.rs       路由、页面、token 校验
  protocol.rs   WS 消息类型（serde 枚举，替代手写 match 字符串）
  hub.rs        会话归属、音频 Inbox、广播
  rtc.rs / tunnel.rs（保持）
```

`protocol.rs` 用 `#[serde(tag = "op")]` 枚举，手机页与 Rust 各自一份契约，拼错立刻能发现。

### 3.3 设置版本化

```rust
pub struct Settings { pub schema: u32, ... }
fn migrate(v: u32, raw: Value) -> Settings  // v1 → v2 → …
```

## 四、执行顺序与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **A. 设计系统** | tokens + 组件库 + 全局样式收口；品牌色统一到暖橙 | 同一张截图里不再出现蓝紫渐变；`style.css` ≤ 40 行；页面无 scoped 视觉样式 |
| **B. 信息架构** | 4 页 → 3 页；连接页状态卡 + 最近一句；设置合并 | 冷启动 5 秒内能回答「能不能用」「用哪个渠道」 |
| **C. HUD** | 新胶囊 + 主题跟随 | 录音/等待/出错三态肉眼可辨 |
| **D. 后端拆分** | 按 3.1 拆文件，行为不变 | `cargo test` 全绿且新增 `machine.rs` 单测；`main.rs` < 120 行 |
| **E. 日志与错误** | 文件日志 + 去掉静默失败 | 拔网线/杀隧道能在日志里看到一行原因 |
| **F. 协议枚举化** | WS 消息改成枚举 | 手改手机页字段名会立刻报错 |

每阶段独立可回滚；A–C 只动前端，D–F 只动后端，互不阻塞。

## 五、两个需要你拍板的设计选择

1. **默认页**：连接（状态优先，推荐）还是渠道（选完就走）？
2. **设置是否保留独立页**：合并进「连接」页的折叠区（更紧凑）还是单列一页（更清楚）？
